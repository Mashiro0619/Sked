# 启动边界与独立进程性能验收

本轮继续补齐全项目重构的启动验收。既有工作区挂载和 `lifecycle.disk_load` 结果保留原边界，不能替代进程创建至首个就绪画面的冷启动时间。

## 通知运行时锁的隔离作用域

`AgendaRuntimeMutationLockScope` 接收明确的绝对锁文件路径。`withAgendaRuntimeMutationLockScope` 将它应用于当前调用及在其中注册的异步回调，通知协调器、通知服务与业务命令沿用原有锁入口。broker 身份由规范化路径确定；显式默认路径与未设置作用域的调用继续使用原 broker。

每份重入令牌绑定锁身份并在释放时失效，因此 A 内获取 B 仍会等待 B，A → B → A 可以复用仍持有的 A。新 broker isolate 显式接收路径与 namespace，业务工作 isolate 也必须自行安装传入的作用域。默认锁文件、消息协议、队列、超时和心跳算法保持不变。

路径规范化不解析符号链接、硬链接或 Windows 短路径别名；调用方需传递同一受检路径。文件访问失败时仍保留原有进程内队列回退，独立启动基准还需证明隔离目录和真实文件锁可用。

保留原有六项锁测试，新增八项作用域行为测试。锁、通知服务、协调器和后台对账的四个文件在 Windows 与 Linux 各通过 163 项。验证包括跨 isolate 串行、跨作用域独立执行、嵌套重入、失效令牌及默认兼容；两个作用域创建的文件经文件身份查询确认不同。测试使用独立临时根，未借用真实应用实例的通知锁。

- Windows 回归：`.scratch/refactor-20261014/startup-notification-lock-scope.log`。
- Linux 候选归档与源文件校验：`.scratch/refactor-20261017/startup/lock-check-20261016T204909259Z/`。
- 静态分析与四份 Dart 文件格式检查通过。

## 启动组合根

`runSkedApp` 统一 binding、系统界面、桌面窗口与许可注册的启动顺序，再创建 `AppBootstrap`。`AppStartupDependencies` 在应用根绑定桌面偏好、开发者界面偏好、通知服务和更新服务；默认工厂沿用现有实现，偏好与通知仍按原生命周期延迟创建。

实例租约取得后才创建运行时与桌面偏好。桌面偏好工厂同步失败时，释放尚未加载的运行时并允许重试；正常退出继续等待数据加载、写入静止和偏好 flush 后释放租约。`MyApp` 缓存注入服务的首页实例，使组合根或无关偏好重建不替换首页；工作区与继承主题的变化仍正常传递。

既有八项 bootstrap 测试保留，新增五个场景覆盖平台调用顺序、延迟工厂与关闭顺序、失败后重试、借用和自有偏好的释放，以及首页身份和更新服务归属。四份相关测试共 119 项通过，格式与静态分析通过。证据为 `.scratch/refactor-20261014/startup-composition-r2.log`；组合根测试主动阻塞通知就绪，不能替代完整启动的通知锁隔离验证。

## 独立进程测量入口

`benchmark/startup_main.dart` 使用普通 Flutter binding 和真实启动组合根，配合 `benchmark/run_startup_windows.ps1` 从 Windows 进程创建时刻记录首帧、就绪帧和日期选择响应。真实文件存储、实例租约、加载流程及通知规划参与执行；fixture 在进程外准备，密钥、网络和 OS 通知使用隔离适配器。普通插件注册器仍可能加载通知 DLL。

探针验证真实 Win32 窗口可见性、实际日期与渲染选中态变化。进程结束前由独立进程证明通知锁和实例锁均产生 Windows 锁冲突，并走正常退出路径。输入通过 Flutter 指针分发，不作为物理鼠标或原生输入投递证据；保留 OS 页、字体与 shader 缓存，测量边界是独立进程启动。

时钟协议 `win32-qpc-precise-filetime-v2` 使用 QPC 前后读数夹住精确 FILETIME；原生偏移、引擎偏移及两者的校准残差均保留 5 ms 门槛。begin 观测在 draw 入口绑定 SDK 已更新的真实帧号；生产 warm-up 和无 Dart begin 的原生重绘单列，不能补造就绪帧。旧探针的两次失败冒烟保存在 `smoke-pair-v1/`，不会转为有效样本。

16 项纯回归覆盖整数溢出、时钟区间、5 ms 边界、帧号归属、warm-up、原生重绘与失效拒绝，并纳入常规测试目录；格式和静态分析通过。修正后的单进程诊断验证了窗口、输入、锁、QPC 和帧号链路；随后互审补齐引擎自身漂移保护并通过上述回归。最终签名构建仍需两侧各三进程、三个数据集的完整矩阵，不能把诊断冒烟充作正式样本。

运行方式、原生可见性和时钟边界详见 [启动测量说明](../benchmark/STARTUP.md)。测试日志为 `.scratch/refactor-20261017/startup/clock-v2/clock-tests.log`；诊断证据为 `.scratch/refactor-20261017/startup/smoke-after-v2/`。当前尚不宣称 Windows 或 Android 冷启动的完整验收完成。

## 分阶段内存观测

`process-rss-v1` 在 Dart 入口、就绪帧报告、响应帧报告及完整校验前的测量结束各读取一次 `ProcessInfo.currentRss` 与 `maxRss`，同时记录精确时钟来源和读取开销。就绪／响应的内存值属于报告被观察的时刻；进程峰值包含入口之前的 native/VM 启动，不能解释为 Dart 堆或恰好在 raster 时刻的用量。采样不发生在每帧。

运行器核对四点顺序、正数 RSS、非下降峰值、原生时钟来源和对应就绪／响应帧，保留原始值、入口差值与每组三个进程的统计。该补充通过格式、静态分析、16 项时钟回归和原生四点采样冒烟；证据在 `.scratch/refactor-20261017/startup/smoke-memory-v1/`。此前 `matrix-v2/` 的 18 个进程已通过时间与交互检查，但没有 RSS；完整时间和内存对比采用补充后的新构建重新采样，不向旧结果补值。
