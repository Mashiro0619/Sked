# Android 通知发布验收

> 状态：**待真机执行**。2026-09-15 复查 `adb devices -l` 仍未发现连接设备。
> 单元测试、模拟网关、Release 编译成功都不能替代这里的真机记录。

## 1. 必须先区分的系统行为

- **后台进程被回收 / `am kill` / 划掉最近任务 ≠ 设置中的“强行停止” / `am force-stop`。** 强行停止会进入 Android 的 stopped 状态；提醒和后台工作不能被承诺继续运行，通常需要用户再次主动启动应用。国产 ROM 对划掉任务也可能另有策略，必须实测，不能照搬 Pixel 结论。
- 广播 receiver 的 `exported=false` 是安全边界，不应为测试改成公开。重启、日期、时区必须通过真实系统操作触发；不能把手工发送受保护广播成功与否当成验收结果。
- 精确闹钟权限撤回可能终止进程并取消未来的精确闹钟。重新授权后的恢复与撤权期间的受阻提示要分别验证。
- 打开电池 / 自启动设置页只代表“已打开设置入口”，**不代表授权成功**。部分厂商不能可靠查询自启动授权状态，必须记录人工确认结果。
- 当前产品坚持精确提醒；权限、渠道或电池条件不满足时应报告受阻，不能静默降级为不精确提醒并显示“就绪”。
- CI 使用一次性测试签名，只验证 Release 编译、混淆、打包。**不能用它覆盖安装真实发布签名的应用，也不能据此证明升级保留密钥。** 升级验收必须使用相同正式测试证书、真实旧版本和相同应用 ID。

## 3. 固定测试数据与准备

1. 使用独立测试数据和无真实权限的合成 API Key，不在真机记录中保存实际凭据或认证头。
2. 记录应用版本、Git SHA、APK SHA-256、签名证书 SHA-256、设备型号、Android 版本、时区、通知权限、通知渠道、精确闹钟权限、电池策略、自启动设置。
3. 至少准备：一条课程提醒、一条普通日程提醒、一条跨天重复日程；设置在操作完成后仍有足够时间触发的提醒。
4. 同时记录预计本地时间和 UTC / epoch 时间，避免把时区显示变化误判成实际触发时间变化。
5. 从应用通知诊断页记录最近排程的模式、来源、结果、覆盖状态、直接排程数量和下次续期时间。不要使用固定 sleep 推断业务同步完成；先等待对应诊断更新。
6. 不清除现有用户数据，不用卸载重装代替升级测试。若需要隔离环境，使用专用设备 / 测试用户。

## 4. 每台设备执行的场景

| 编号 | 操作 | 预期 / 需要核对的现象 |
| --- | --- | --- |
| N01 | 首次冷启动并完成必要授权 | 持久化快照与计划一致；诊断更新；提醒只出现一次 |
| N02 | 修改提醒开关、提前时间、日程时间和内容 | 旧计划被替换，不重复、不遗漏；新诊断对应新快照 |
| N03 | 返回桌面，后台等待 | 提醒按计划触发；点击和操作路由正确 |
| N04 | 后台执行 `am kill`，以及单独测试划掉任务 | 区分系统回收和厂商任务清理；已登记提醒与冷启动恢复不重复 |
| N05 | 设置页强行停止 / `am force-stop`，然后主动重开 | stopped 期间不承诺通知；主动重开后读取实际权限并重新建立正确计划 |
| N06 | 手机真实重启，解锁后保持应用未手动打开 | 检查重启恢复与即将到期提醒；记录厂商是否阻止自启动 |
| N07 | 同签名 `adb install -r` 升级安装 | 数据和测试密钥保持；升级恢复无重复提醒；不能换签名替代 |
| N08 | 日期跨日 / 手动修改时间 | 未来计划刷新；过期提醒不被大批重放；近到期恢复窗口单独记录 |
| N09 | 上海、纽约、柏林之间切换时区 | 新计划使用新时区，不复用初始化时缓存的时区；核对 UTC 时刻与本地显示 |
| N10 | 撤回通知权限 / 禁用实际使用的通知渠道，再恢复 | 受阻状态真实；恢复后重新排程；未使用渠道的禁用不误伤其他提醒 |
| N11 | 撤回精确闹钟权限，再重新授权并回到应用 | 受阻而非假成功；不静默降级；重建被系统取消的提醒 |
| N12 | 启用电池优化，然后解除 | 当前策略下先受阻、解除后恢复；打开设置页本身不是通过条件 |
| N13 | 关闭厂商自启动，再恢复 | 人工记录真实设置与后台表现；不把“入口可用”当“已授权” |
| N14 | 使用测试构建注入一次平台排程失败，再解除故障 | 旧有效计划不被无条件清空；失败诊断可见；重试成功替换失败诊断 |
| N15 | 在开发诊断页重复创建立即 / 延迟测试通知 | 测试记录独立；不替换真实日程提醒；清理运行时不影响普通数据 |
| N16 | 在提醒到期前后重启 / 恢复 | 验证近到期保护窗口，不丢弃刚到期提醒；窗口外不重复播放过期提醒 |
| N17 | 按录屏场景：09:00 日程提前 5 分钟，08:55 内多次点通知／开关详情／切前后台 | 应只出现原提醒，不因通知退出 pending 列表而每 5 秒补发；记录每次实际横幅、响铃及登记次数 |
| N18 | 在历史起点建立后才发现一条刚过触发点的未登记提醒，连续恢复并重启 | 1 分钟窗口内只安排一次 5 秒后的补发；时间固定；触发后或滑掉后不重放 |
| N19 | 同一通知卡片重复消费“稍后 10 分钟”；稍后通知触发后再主动选择稍后 | 旧动作使用原凭据、不重新计时；新卡片的明确动作可产生新的稍后提醒 |
| N20 | 分别执行普通运行时清理与完整数据清除，再恢复 | 普通清理不抹除登记证据；完整清除隔离旧代际，旧后台任务不能回写或再投递 |

N14 的注入应由可控测试构建完成；撤回精确闹钟权限属于已知能力受阻，不是模拟任意平台故障的等价替代。

## 6. 辅助命令（由真机执行者按需运行）

以下命令不改变应用数据，但终止进程会中断当前操作。先确认处于专用测试环境。

```powershell
adb devices -l
adb shell getprop ro.product.model
adb shell getprop ro.build.version.release
adb shell getprop ro.build.version.sdk
adb shell getprop persist.sys.timezone
adb shell input keyevent 3
adb shell am kill com.mashiro.sked
# 单独验证 stopped 状态；不要和普通进程回收混为一谈。
adb shell am force-stop com.mashiro.sked
# 再通过桌面图标主动启动应用，检查恢复诊断。
```

升级测试在确认 APK 来自可信构建且证书一致后执行 `adb install -r <test-release.apk>`。不使用 `pm clear`，不删除用户存储来让测试“通过”。

## 7. 发布门禁

- 不漏发、不异常重复、不把失败或受阻显示为已就绪；实际触发偏差必须记录。精确提醒的产品级延迟阈值尚未定义，不自行伪造验收 SLA。
- 每个未覆盖设备 / 场景必须进入发布风险说明；没有真机记录时不得声称完成通知可靠性验收。
- 软件回归的作用是证明输入、状态迁移和恢复边界；原生广播交付、厂商后台限制和真实触发时刻仍以本表证据为准。


## 8. 重复通知修复的判读边界（2026-09-15）

- 运行时登记状态 `accepted` 仅代表平台接受排程，不代表已展示；`pending` 也可能是崩溃／系统调用结果不明，按“优先避免重复”抑制自动补发并保留诊断。
- 只有明确没有提交给系统的失败才自动重试逾期补发。撤权、厂商终止进程等不确定状态可能无法兼得不漏发与不重复；不能把重复静音视为修复，也不能声称绝对恰好送达一次。
- 首次升级以前没有证据的逾期提醒不盲目重放；以后在通知关闭／权限受阻时已经观察到的未来提醒，在重新允许且原时间仅过去 1 分钟内，可按未登记规则补发一次。
- 通知设置 UI 不变；`registrationDecisions`、`duplicatePendingRemoved` 是底层诊断记录字段。取证时同时保留它们和原生待发／已显示列表，不把列表计数当实际响铃次数。
- Windows 的独立原生队列测试、运行时契约与待执行人工场景见 [通知防重记录](NOTIFICATION_DEDUPLICATION.md)。Windows 队列通过不能替代本文件的 Android 真机记录。
